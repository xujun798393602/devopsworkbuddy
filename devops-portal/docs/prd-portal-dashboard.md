# PRD — DevOps 平台门户首页 / 驾驶舱（简单 PRD）

> 文档模式：简单 PRD（默认模式，无竞品分析）
> 语言：中文
> 前端技术栈：Vue 3 + Vite + Vuetify 3
> 后端技术栈：Python 3 + Flask 微服务
> 项目代号：`portal_dashboard`
> 原始需求复述：门户首页需「统一千人一面」（所有用户布局一致，不按角色差异化）；首页聚合展示平台数据，允许跨项目查看，但需权限管控——**仅当用户在权限配置中勾选「跨项目查看」权限时才可跨项目**；否则仅聚合当前用户参与的项目数据。本次走标准 SOP 完整开发。

---

## 1. 产品目标

为所有登录用户提供**统一一致（千人一面）**的平台数据聚合首页，让用户在一个页面内纵览其参与项目的「项目 / 需求 / TP / TD」关键进展；并在持有「跨项目查看」权限时聚合全平台数据，提升信息获取效率与决策速度。

---

## 2. 用户故事

- **作为普通成员（未勾选跨项目查看权限）**，我希望首页只聚合我参与的项目数据，以便专注自身工作、不被无关项目干扰。
- **作为跨项目查看权限用户**（权限配置中已勾选「跨项目查看」），我希望首页能聚合全平台所有项目数据，以便掌握整体进展与质量态势。
- **作为项目经理 / 管理员**，我希望首页直接呈现待我审批、待我处理的事项及各部门汇总统计，以便快速跟进阻塞与风险。
- **作为测试 / 开发人员**，我希望首页呈现「我的待办 / 我的缺陷 / 我的待执行用例」计数与入口，以便一键进入处理。
- **作为任何用户（无论角色）**，我希望看到的门户首页布局完全一致（千人一面），以避免角色差异化首页带来的认知割裂。

---

## 3. 需求池（优先级）

### P0（必须）

- **统一首页布局（千人一面）**：所有角色看到相同的首页结构与卡片排布，不按角色差异化渲染。
- **我的项目概览卡片**：展示当前用户参与的项目（项目名、当前迭代/版本、进度）。数据源：`project-service`。
- **待办 / 待审区**：聚合当前用户的待办任务、待审需求/流程、分派给我的未关闭缺陷等。数据源：`workflow` / `td` / `tp` / `project-service`。
- **关键统计区**：按业务域聚合核心指标——需求条目数、TP 用例/执行数、TD 缺陷数（按状态分布）。数据源：`requirement-service` / `tp-service` / `td-service`。
- **跨项目查看权限开关与默认行为**（权限点建议命名 `portal:cross-project-view`，默认**关闭**）：
  - 未勾选 → 仅聚合当前用户参与的项目数据（`scope=mine`）。
  - 已勾选 → 可聚合跨项目（全平台）数据（`scope=cross-project`）。
- **聚合数据接口（P0 架构建议）**：网关新增 BFF 聚合接口 `/bff/api/portal/dashboard`，由网关**并行**调用 `project/requirement/tp/td` 等各业务域服务后汇总为单份数据返回，前端只发 1 个请求（避免前端发 N 个请求）。
- **🔴 权限校验红线（强制 P0）**：跨项目查看权限的校验**必须放在后端**（网关或业务服务）。前端仅在探测到自身拥有该权限点时才请求跨项目数据；**能否跨项目的最终判定由网关 / IAM 基于 `X-Platform-Permissions` 决定，前端无权自决**。

### P1（重要）

- **最近动态 / 通知流**：展示当前用户相关的近期活动与通知。数据源：`notification-service` / `audit`。
- **快捷入口区**：常用功能快捷跳转（新建需求、提交缺陷、我的项目、测试设计等），链接到各业务域视图。
- **按业务域分组的数据卡片**：项目 / 需求 / TP / TD 四个分组，每组一张汇总卡片，结构清晰。

### P2（增强）

- **图表可视化**：缺陷趋势、需求燃尽、测试覆盖率等轻量图表（注意门户已有 theme 机制，图表需适配主题）。
- **收藏 / 置顶**：允许用户将常用项目或卡片置顶 / 收藏。
- **深色模式切换**：复用门户已有 theme 机制，不重新造轮子。

## 4. UI 设计稿（首页布局 · 千人一面）

```
+----------------------------------------------------------------------+
|  顶部导航栏 (Top App Bar) — 全局一致                                  |
|  [Logo] DevOps 平台   [全局搜索?]            [通知铃] [用户头像/菜单]  |
+----------------------------------------------------------------------+
|  主体区（卡片网格，所有用户布局一致；移动端单列）                       |
| +-----------------------------+  +-----------------------------+     |
| | 我的项目概览 (Project)        |  | 待办 / 待审 (My Work)         |    |
| | - 项目A  迭代1   65%         |  | - 待审需求 3                  |    |
| | - 项目B  版本2.0 进行中       |  | - 分派给我未关闭缺陷 5         |    |
| | [查看全部 ->]                |  | - 待执行用例 12               |    |
| | 数据源: project-service       |  | 数据源: workflow/td/tp/...     |   |
| +-----------------------------+  +-----------------------------+     |
| +-----------------------------+  +-----------------------------+     |
| | 需求统计 (Requirement)         |  | TP 测试统计 (TP)              |   |
| | 需求条目 N / 基线 M            |  | 用例库 X / 执行中 Y / 通过 Z  |   |
| | 数据源: requirement-service    |  | 数据源: tp-service            |   |
| +-----------------------------+  +-----------------------------+     |
| +--------------------------------------------------------------+     |
| | TD 缺陷统计 (TD)   新增 N / 修复中 M / 已关闭 K   质量概览       |    |
| | 数据源: td-service                                             |    |
| +--------------------------------------------------------------+     |
| +--------------------------------------------------------------+     |
| | 最近动态 / 通知流 (P1)   数据源: notification / audit           |   |
| +--------------------------------------------------------------+     |
+----------------------------------------------------------------------+
|  侧边 / 快捷区（可选，与主体一致，不按角色变化）                       |
|  [快捷入口] 新建需求 / 提交缺陷 / 我的项目 / 测试设计                 |
+----------------------------------------------------------------------+
```

**布局约定**
- 顶部导航：全局一致，含品牌、全局搜索（是否 P0 见待确认问题）、通知、用户菜单。
- 主体卡片网格：固定 2 列（移动端 1 列），卡片顺序固定（项目概览 → 我的工作 → 需求 → TP → TD → 动态），**不随用户角色变化**。
- 跨项目范围标识：当当前用户持有跨项目查看权限时，卡片标题旁显示「全平台」标签；否则显示「我的项目」。该标识为纯展示层，不改变布局结构。

## 5. 权限模型约定

- **权限点命名**：建议 `portal:cross-project-view`（字符串 permission）。
- **默认状态**：默认**关闭**（未勾选），即仅聚合当前用户参与的项目数据。
- **配置位置**：在 IAM 权限配置中为角色 / 用户勾选该权限点；IAM 签发 token 时将其纳入 `X-Platform-Permissions`。
- **前端行为**：
  - 前端从 `X-Platform-Permissions`（或 session 接口 `/bff/session`）判断是否持有该权限点。
  - 若持有，请求聚合接口时携带 `scope=cross-project`；否则携带 `scope=mine`（或省略，后端默认 `mine`）。
  - 前端**只负责展示与发起请求，不决定能否跨项目**。
- **后端校验（安全红线）**：
  - 网关 `/bff/api/portal/dashboard` 收到请求后，**必须**基于 `X-Platform-Permissions` 校验 `portal:cross-project-view`。
  - 若请求 `scope=cross-project` 但权限点缺失，**网关必须拒绝或降级为 `mine`**，绝不允许前端越权获取全平台数据。
  - 各业务域服务聚合时遵循最小权限原则（仅查当前 actor 可见范围）；网关注入的 `X-Actor-Id` 用于限定「我的项目」范围。

## 6. 待确认问题（需客户 / 架构师拍板）

1. **数据实时性**：首页统计是实时查询还是允许缓存（如 1–5 分钟）？影响聚合接口性能与数据库压力。
2. **分页 / 数量上限**：项目概览、动态流是否分页？单卡片默认展示条数（如 5 / 10 条）？
3. **是否需要全局搜索**：顶部搜索框是否纳入本期（P0）？跨项目搜索权限是否绑定 `portal:cross-project-view`？
4. **空状态处理**：用户无参与项目 / 无待办时首页如何呈现（引导创建 / 空插图 / 占位文案）？
5. **「我的项目」范围定义**：以用户在 `project-service` 中的成员关系为准，还是含「关注 / 被分派」？需与 `project-service` 对齐成员边界。
6. **聚合接口字段契约**：各业务域需提供哪些最小字段？建议架构师拉各服务负责人对齐响应 schema。
7. **刷新策略**：手动刷新 vs 定时轮询（如每 60s）？首屏骨架屏（skeleton）是否必需？
8. **跨项目入口可见性**：未授权用户是否应知道「存在跨项目视图」？（建议隐藏入口，仅授权用户可见「全平台」切换。）
