# 公司级 DevOps 管理平台总体设计规格

- 文档状态：已评审
- 版本：1.0
- 日期：2026-08-01
- 适用规模：500～5000 名研发用户、200～2000 个项目

## 1. 建设目标与范围

建设统一的公司级 DevOps 管理平台，覆盖项目、需求、TP 测试管理、TD Bug 缺陷管理，并与 GitLab、GitLab CI/CD、Nexus、Harbor 深度集成，形成从需求到发布的端到端追溯和质量治理闭环。

一期业务范围：

1. 项目管理：项目、成员、迭代、阶段、里程碑、版本、任务和工时。
2. 需求管理：Epic、Feature、US、FR、NFR、AC、基线和变更。
3. TP 测试管理：AI 需求分析、XMind 测试设计、用例库、计划、执行、自动化和报告。
4. TD 缺陷管理：提交、分派、修复、验证、关闭、重开和质量分析。
5. 研发交付治理：GitLab 代码评审、GitLab CI/CD、代码门禁、Nexus/Harbor 制品和发布。
6. 公共治理：IAM、工作流、审计、通知、搜索、度量和可观测性。

代码托管、流水线执行和二进制仓库不重复自研：GitLab 负责代码与 MR，GitLab Runner 负责作业执行，Nexus/Harbor 保存正式制品；平台负责统一编排、门禁、权限、追溯、审批和度量。

## 2. 已确认技术基线

| 类别 | 选型 |
|---|---|
| 后端 | Python 3 + Flask，Gunicorn 生产运行 |
| 前端 | Vue 3 + TypeScript + Vite + Pinia |
| API | REST + OpenAPI 3，前端生成 TypeScript 客户端 |
| 数据库 | PostgreSQL，服务私有 Database |
| 缓存 | Redis |
| 消息与任务 | RabbitMQ + Celery |
| 对象存储 | MinIO |
| 搜索 | OpenSearch |
| ORM/迁移 | SQLAlchemy 2 + Alembic |
| CI/CD | GitLab CI/CD + GitLab Runner |
| 制品 | Nexus + Harbor |
| 可观测性 | Prometheus、Grafana、Loki/OpenSearch、OpenTelemetry、Tempo |
| 部署 | 一期 Docker 多主机，后续 Kubernetes |

## 3. 总体架构

采用同步 REST API 与异步领域事件混合的微服务架构：

```text
Vue 3 统一门户
  ↓
API Gateway / BFF
  ├── 同步 REST：查询、命令、权限校验、门禁评估
  └── Webhook：GitLab 等外部系统事件
        ↓
核心领域服务
  IAM | 项目 | 需求 | TP | TD | 工作流 | 发布
        ↓
支撑与集成服务
  AI模型网关 | XMind | GitLab集成 | CI/CD治理 | 制品 | 通知 | 审计 | 搜索 | 度量
        ↓
RabbitMQ + Celery
  Outbox | 幂等消费 | 重试 | 死信 | 补偿
        ↓
PostgreSQL | Redis | MinIO | OpenSearch | Nexus | Harbor | GitLab
```

关键约束：

- 核心业务数据按服务私有，禁止共享数据库和跨服务外键。
- 跨域即时操作走 REST；状态传播、AI 任务、GitLab 回调、通知、审计、搜索和度量走事件。
- 跨服务一致性采用 Outbox、幂等、重试和补偿，不使用分布式强事务。
- 同步调用链原则上不超过三级；复杂查询使用 BFF 并行聚合或查询投影。
- 所有操作携带 `project_id`、`operator_id` 和 `trace_id`。
- 外部系统均通过适配器/防腐层接入。

## 4. 服务边界

### 4.1 核心服务

| 服务 | 核心职责 |
|---|---|
| IAM | SSO、LDAP/AD 同步、角色、项目权限、服务身份 |
| 项目 | 项目、成员、模板、迭代、阶段、里程碑、版本、任务、工时 |
| 需求 | Epic、Feature、US、FR、NFR、AC、基线、变更和影响分析 |
| TP | 测试设计、用例库、计划、轮次、任务、执行、自动化、报告和追溯 |
| TD | Bug 生命周期、修复验证、根因、版本和质量分析 |
| 工作流 | 模板、状态、流转、审批、待办和门禁动作 |
| 发布 | 发布单、部署、回滚、发布门禁和追溯快照 |

测试用例不拆为独立服务，归入 TP 统一管理。XMind 服务是无状态技术服务；AI 模型网关只负责模型调用治理，不持有正式测试业务数据。

### 4.2 支撑服务

- GitLab 集成：项目映射、Webhook、Commit、MR、Pipeline 和用户映射。
- CI/CD 治理：模板、触发、状态同步、质量门禁和测试调度。
- 制品：Nexus/Harbor 元数据、签名、扫描、晋级和追溯。
- 审计：身份、权限、业务、集成、AI、数据和运维审计。
- 通知：站内信、邮件、企业通信渠道和订阅。
- 搜索：跨项目统一检索。
- 度量：研发效能、交付、质量和测试指标聚合。

## 5. 项目管理与任务效能

项目支持 Scrum、瀑布和混合模板。版本下可关联需求、任务、测试计划、制品、发布和缺陷。

任务核心字段：任务类型、负责人、参与人、优先级、状态、迭代、版本、计划起止时间、实际起止时间、预估工时、剩余工时、关联需求、缺陷、分支和 MR。

实际工时使用不可覆盖的 Worklog 明细累加，记录人员、日期、耗时、内容和修正审计。任务至少关联迭代或版本之一。

主要统计：迭代燃尽、计划准确度、准时交付率、需求周期时间、成员负荷、阻塞时间、资源分布和技术债趋势。工时用于资源规划和过程改进，不作为个人单一绩效排名。

## 6. 需求管理

需求层级：

```text
Epic → Feature → User Story → FR / NFR / AC
```

需求评审通过后形成不可变基线快照。基线后变更必须提交变更申请，包含原因、影响范围和紧急程度；审批后生成新版本，并发布 `Requirement.BaselineChanged` 事件。

平台支持从需求追溯到设计、用例、执行、缺陷、修复代码和发布，也支持反向追溯。需求变更后，相关测试设计和用例自动标记为“待评估”。

## 7. TP 测试管理与 AI 测试设计

### 7.1 AI + 人工评审链路

```text
选择需求并创建快照
→ AI 需求分析草稿
→ 人工确认
→ AI 生成测试设计 XMind
→ 人工评审
→ AI 生成测试用例 XMind
→ 格式、重复、覆盖和可执行性校验
→ 选择目标用例文件夹与冲突策略
→ 导入正式用例库
→ 建立需求—设计节点—用例追溯
```

AI 输出始终为草稿。每次调用保存输入快照、模型、提示词版本、知识库版本、参数、Token、成本、耗时、结果版本、操作人、评审意见和采纳率。

模型网关同时接入公司私有模型和获准外部模型，按项目数据密级、任务类型、模型能力、成本和可用性路由，不允许降级绕过安全策略。

### 7.2 XMind 与用例

- 保存原始 `.xmind`、解析后的节点、层级、标签和版本。
- 建立 XMind 节点与结构化用例 ID 的映射。
- 重复导入支持新增、更新、跳过和冲突处理。
- 人工修改后的正式用例不得被 AI 静默覆盖。
- 需求、XMind、用例和导入批次均保留版本关系。

### 7.3 测试计划与自动化

测试计划关联版本、需求范围、用例、环境、轮次、测试任务和准出标准。TP 管理自动化资产和结果，通过 GitLab CI/CD 与专用 Runner 执行。

一期建立通用适配协议并重点支持 API、Web UI、Android App 和 Android TV；统一任务输入、状态、日志、附件和 JUnit XML/Allure/JSON 结果。失败用例经确认创建 TD，缺陷修复后触发回归。

## 8. TD 缺陷管理

标准状态：新建、已分派、处理中、已拒绝、已修复、待验证、已关闭、重开。

缺陷记录严重程度、优先级、类型、根因、引入阶段、发现阶段、影响/发现/修复版本、需求、用例、执行、任务、Commit/MR 和附件。

关键门禁：

- 已修复转待验证：必须关联已合并 MR 和修复版本。
- 待验证转关闭：必须记录验证环境、结果和回归证据。
- 发布：P0/P1 全部关闭，P2 达到项目阈值。
- 重开达到阈值：自动升级并通知负责人。

核心度量包括缺陷逃逸率、重开率、平均修复/验证时长、根因分布、引入阶段、模块分布和自动化捕获率。

## 9. GitLab、CI/CD、制品与发布

### 9.1 GitLab 集成

平台项目映射一个或多个 GitLab 项目。分支建议使用 `feature/{需求ID}`、`task/{任务ID}`、`bugfix/{缺陷ID}`、`release/{版本号}` 和 `hotfix/{缺陷ID}`。

Webhook 必须验签后快速入队，异步处理 Push、MR、Pipeline 和 Tag 事件。GitLab 用户通过统一身份不可变 ID 映射平台用户。

### 9.2 代码门禁

MR 合并前检查：关联需求/任务/缺陷、命名规范、CI 成功、单元测试、覆盖率、静态检查、依赖和安全漏洞、CODEOWNERS、评审人数、追溯完整性。紧急绕过必须审批和全量审计。

### 9.3 制品和发布

GitLab 临时产物保存测试报告和日志；正式软件包进入 Nexus，镜像进入 Harbor。坚持“一次构建、多环境晋级”，测试、预发布和生产使用同一 SHA256 制品。

发布单包含需求/缺陷/任务范围、制品、环境计划、回滚方案、审批和追溯快照。发布门禁聚合需求基线、测试覆盖、测试执行、缺陷状态、安全扫描、制品验证、MR 评审和回滚准备情况。

## 10. IAM、权限与项目隔离

认证优先使用 OIDC/OAuth 2.1，兼容 LDAP/AD，同步用户和组织。保留隔离的本地应急管理员，强制 MFA、IP 白名单、凭据轮换和全量审计。

授权采用 RBAC + ABAC + 数据范围：角色决定可执行动作，属性策略决定对象/环境约束，数据范围默认限制为用户参与项目。平台管理员不自动拥有全部业务数据查看权限。

网关负责认证和基础限流，业务服务执行最终对象级鉴权；异步任务、导出和跨项目汇总不得绕过权限体系。

## 11. 模板化工作流与审计

一期提供项目、需求、测试设计、测试计划、缺陷、制品晋级、发布和紧急变更模板。项目可受控调整状态名称、审批角色、人数、必填字段和质量阈值，不允许任意脚本、SQL 或绕权操作。

流程实例绑定模板版本快照，状态迁移使用乐观锁和幂等键；外部调用失败进入重试或补偿。

审计记录至少包含时间、Trace、主体、项目、资源、动作、前后差异、来源、结果和审批/绕过单 ID。审计采用追加写入，业务服务不能修改或删除。

## 12. API、事件与数据一致性

### 12.1 API

- 前缀 `/api/v1`，JSON 使用 `snake_case`。
- 写操作支持 `Idempotency-Key`。
- 更新使用 `If-Match` 或 `version` 乐观锁。
- 错误使用 RFC 9457 Problem Details。
- 状态转换使用显式动作 API，客户端不得任意写 `status`。
- OpenAPI 是接口契约源，并生成 Vue TypeScript 客户端。

### 12.2 事件

事件信封包含 `event_id`、`event_type`、`event_version`、`occurred_at`、`producer`、`trace_id`、`project_id`、`actor`、`aggregate`、`data` 和数据密级。

事件采用“对象 + 已发生事实”命名，每类事件维护 JSON Schema 并纳入 CI 兼容性检查。

可靠性流程：业务数据与 Outbox 同事务提交 → 发布至 RabbitMQ → 消费端按事件和消费者幂等 → 指数退避重试 → 死信 → 受控重放或人工补偿。

## 13. 数据与查询

每个服务拥有独立 Database 和账号；一期可共享 PostgreSQL 高可用集群。正式资产不物理删除，使用关闭、废弃或归档。

核心对象使用 UUIDv7/ULID 技术 ID 与可读业务编号。跨域关系通过业务 ID、版本和追溯关系维护，不建立跨服务外键。

查询策略：单域查询访问所属服务；少量跨域详情由 BFF 并行聚合；全链路追溯、搜索和驾驶舱使用事件构建的只读投影与预聚合，禁止驾驶舱实时扫描业务库。

## 14. 性能、可用性与安全

### 14.1 容量基线

- 注册用户 5000、峰值在线 1500。
- 峰值 API 500～1000 RPS，可水平扩容。
- 普通查询 P95 ≤ 500 ms，写操作 P95 ≤ 800 ms。
- 搜索 P95 ≤ 2 秒，驾驶舱 ≤ 3 秒。
- 事件正常 P95 延迟 ≤ 5 秒。
- AI/XMind 请求在 2 秒内异步受理。
- 年新增业务记录百万级。

上述为设计和压测基线，需通过生产等价环境验证。

### 14.2 高可用与容灾

一期单机房高可用：网关和无状态服务至少双实例，PostgreSQL 主备，Redis、RabbitMQ、MinIO 具备副本与恢复能力。目标 99.9%，RPO ≤ 15 分钟、RTO ≤ 2 小时。

每季度执行恢复演练，验证数据库时间点恢复、消息重放、对象存储恢复和外部系统降级，而不是只检查备份任务状态。

### 14.3 安全

- 凭据不得进入代码、镜像或日志。
- 外部输入、Webhook、文件和 AI 内容必须校验、限额和脱敏。
- 大文件使用 MinIO 预签名上传。
- 生产导出支持审批、水印、数量限制和过期下载。
- 依赖、镜像、代码、密钥和 API 兼容性纳入流水线门禁。

## 15. Docker 到 Kubernetes 演进

Docker 阶段使用同一生产镜像、多主机部署、健康检查、优雅停机和外部配置；Compose 仅用于开发与集成测试，不作为生产高可用编排器。

迁移映射：容器实例到 Deployment，有状态组件到 StatefulSet/托管服务，Nginx 到 Ingress/Gateway API，配置到 ConfigMap/Secret，数据到 PVC/CSI，多实例到 Replica/HPA，发布脚本到 Helm/GitOps。业务 API 和事件协议保持不变。

## 16. 测试与验收

测试层级：单元、数据库/消息集成、API 契约、事件契约、端到端、安全、容量和故障演练。

必须具备自动化黄金链路：

```text
需求与版本
→ 任务与工时
→ GitLab MR 与门禁
→ 构建制品
→ 测试计划与执行
→ 创建 TD
→ 修复与回归
→ 制品晋级和发布
→ 全链路追溯验证
```

高风险模块（IAM、权限、发布、门禁、迁移）必须覆盖单元、集成、契约、E2E 和安全测试。

## 17. 团队能力与代码质量治理

建立轻量工程技术委员会，由架构、后端、前端、测试、SRE、安全负责人和各服务 Tech Lead 组成。每个服务必须有负责人、备份维护者、CODEOWNERS、运行手册和技术债清单。

资深开发在需求澄清、技术方案、关键建模、服务骨架、MR、测试发布和故障复盘阶段介入；采用导师制、结对编程、示范 MR、设计诊所和代码门诊。

能力阶梯：L1 按规范交付、L2 独立负责模块、L3 负责服务质量与指导成员、L4 跨域治理和沉淀标准。晋级使用设计、关键 MR、故障处理、质量改进和指导成果，不使用代码行数、Commit 次数、在线时长或工时总量排名。

每个 Flask 服务采用 Feature-first 结构，API/Service/Repository 职责分离；配置集中校验、输入边界验证、类型化错误、结构化日志、Alembic 迁移、Celery 长任务、健康检查和优雅停机均为强制基线。

自动门禁包括 Ruff、mypy/Pyright、pytest、ESLint、TypeScript、Vitest、Playwright、SonarQube、Bandit、pip-audit/npm audit、Trivy、Gitleaks、OpenAPI diff 和事件 Schema 兼容性。

## 18. 分阶段实施

### 阶段 1：平台底座

交付门户、网关、IAM、项目、版本、迭代、任务、工时、工作流、审计、通知、RabbitMQ/Outbox、可观测性和 Docker 高可用标准。验收：登录、建项目、授权、建版本/任务、登记工时、基础统计闭环。

### 阶段 2：需求、TP、TD

交付需求基线、AI 模型网关、XMind、用例、计划、执行、报告、自动化适配、TD 和完整追溯。验收：需求 → AI/人工评审 → XMind → 用例导入 → 测试 → 缺陷 → 修复回归。

### 阶段 3：GitLab 与发布

交付 GitLab 映射、MR/Commit/Pipeline、代码门禁、Runner 调度、Nexus/Harbor、制品晋级、发布与回滚。验收：需求/任务 → MR → 门禁 → 制品 → 测试 → 修复 → 晋级 → 发布。

### 阶段 4：规模治理

交付统一搜索、管理驾驶舱、指标治理、容量成本、安全运营、Kubernetes/Helm/GitOps 和同城容灾预研。

## 20. 关键风险与控制

| 风险 | 控制措施 |
|---|---|
| 一期微服务过多导致交付失控 | 分阶段交付、黄金样板、契约优先、严格服务边界 |
| 分布式一致性问题 | Outbox、幂等、重试、补偿、对账和死信运维台 |
| AI 结果污染正式资产 | 草稿隔离、人工门禁、版本审计、冲突处理 |
| 指标诱导错误行为 | 聚焦系统和团队趋势，不以单一个人指标排名 |
| Docker 生产高可用不足 | 多主机、双实例、健康检查、标准发布和恢复演练 |
| GitLab/模型等外部故障 | 防腐层、超时、熔断、入队缓冲、降级且不绕安全策略 |
| 公共 SDK 演化为分布式单体 | 禁止共享业务实体和领域逻辑，独立契约版本 |

## 21. 设计结论

本方案以项目、需求、TP、TD 为核心业务域，以 GitLab CI/CD、Nexus、Harbor 为执行与制品基础，以 IAM、工作流、审计、AI 模型网关和度量作为统一治理能力。通过同步 API + 异步事件、服务私有数据、项目级隔离、人工质量门禁和分阶段实施，支撑中大型研发组织逐步建立可追溯、可度量、可扩展的研发管理与交付平台。
